Our harness, how it runs every day

One dispatcher, 119 checks, child sessions with receipts, and a measured model floor.▸

The harness sits on top of Claude Code. It has three layers. Laws are written rules, one rule per line. Checks are hook scripts that refuse a broken act. Tools are small scripts the agents call by name.

1.1 Routing: who decides what

The owner decides four things. Agents decide the rest, and checks decide "done".▸

A request enters one main session. That session picks the route, then hands work down.

1. RequestThe owner types an order into the main session.
2. RouteA prompt hook names the skill that already does the job.
3. Hand downSmall jobs go to an agent lane. Big jobs get a child session.
4. GateChecks refuse a bad act the moment it happens.
5. CloseA turn-end check refuses "done" without proof.
DecisionWho decidesThe rule behind it
Which skill does the jobThe main session, nudged by a hookA skill is read in full before use. A hook names the matching one.
Which model and effortThe measured floor tableEvery spawn runs at its class floor. Going above needs a written reason.
Agent or child sessionThe main sessionA research question inside a big goal gets its own session at once.
Whether work is doneThe turn-end checksA claim needs its same-turn probe. A failure seen is fixed in that run.
A clear recommendationThe agent applies itA clear choice is never parked for the owner.
Send, login, publish, moneyThe owner onlyA message to a person goes out only on the owner's typed word.

1.2 The hook dispatcher and its checks

One process per hook event runs every check. Pre-tool checks fail closed.▸

Claude Code can start one process per hook. We had about 30 starting at once on every call. Now one dispatcher process runs every check of an event. Each check has its own time budget. A hung check decides nothing, and the rest still run.

If the dispatcher itself crashes before a tool call, the call is blocked. A check is added in one manifest file, then tested both ways.

Hook eventChecksDeadlineTypical job
Before a tool call6290 sRefuse a risky command or edit
After a tool call990 sCheck text a write just added
On each prompt15120 sName the right skill, keep standing orders
At turn end3390 sRefuse "done" without proof
Total119-Plus 13 hooks registered directly

Kill switches. Every check has one. *_CHECK=off turns a check off. *_OK="<reason>" lets one act through and logs the reason.

The rule of thumb. A written rule is forgotten under momentum. A script is not. So each repeated mistake becomes a law and, when checkable, a check.

1.3 Sessions, children and task boards

Work moves between sessions as board rows and child sessions, each with a receipt.▸

We do not keep standing peer sessions. A main session spawns a child per task, then closes it. Every hand-off leaves a record another session can read.

1.4 The model floor

Each task class runs at the cheapest model and effort that passed 10 of 10 planted-answer runs.▸

What we took from the KOZHA.I setup, and why

2 adopted, 17 we already had, 3 not for us, 1 not built yet. 23 rows.▸

We read the KOZHA.I public page in full and compared it item by item. Two items filled real gaps. We rebuilt both with a pass count and a narrower trigger.

AdoptedThe gap it closedWhat we builtProofOff switch
adopt Fire line per checkOur log said "some check refused", never which one.The dispatcher writes one row when a check denies, asks, warns or crashes. fire_rates.py prints runs, fires and sessions per check.19 of 19 new tests. Self-test 5 of 5. Eight older suites still pass. A live refusal logged under the right name.GUARD_TELEMETRY=off
adopt Durability guardNothing stopped a hand-typed delete of unpushed work.A worktree removal or a forced branch delete is refused only when it would lose the only copy.15 of 15 tests: 4 refusals, 8 near-misses that pass. A live run refused a delete and passed a listing.DURABILITY_OK="<why>" for one act

The KOZHA.I durability guard denied 829 of 829 checks, because it logs only refusals. Ours triggers only on real loss, and the fire line counts its passes. In its first window it ran 265 times and refused none.
